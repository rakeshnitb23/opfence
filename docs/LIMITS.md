# What Opfence does not protect against

Opfence reads the requests a coding agent makes to cloud APIs, decides each operation from a tested catalog, and keeps real API keys out of the agent's reach. This page lists what that does not cover, so you can decide what else you need. Each item says what happens instead.

## Ways around the proxy

- **Weak mode.** `opfence run --weak` sets proxy variables but no sandbox, so a program can ignore them and connect directly. Use it only for tools you trust; the banner and every approval card say the session is unsandboxed.
- **A sandbox setting that loosens it.** Opfence passes its settings to Claude Code with `--settings`; a managed or user settings file can still add allowed domains or unsandboxed commands. `opfence run` warns about the ones it knows, and `opfence doctor --probe` checks from inside the sandbox what an agent can actually reach.
- **Gemini CLI's and Cursor's config files that do not exist yet** (`~/.gemini/settings.json`, a project's `.cursor/mcp.json` when `.cursor` exists) cannot be kept from being created without stopping the agent, so the sandbox can create them. They can add MCP servers or hooks that run the next time you start the agent outside Opfence; `opfence run` names any that were created when the session ends.
- **The agent's own backend.** Under `opfence run --srt`, Codex, Cursor and Gemini CLI reach their model and sign-in hosts through a tunnel Opfence does not inspect. Opfence decides cloud API calls, not what an agent sends to its model.
- **Hosts on the passthrough list** (package registries and GitHub's download hosts) are tunnelled without inspection. A client can send a different `Host` header inside such a tunnel (domain fronting); Opfence checks the TLS server name, not what is inside the encrypted session. The built-in hosts are tunnelled on port 443 only; hosts you add yourself are tunnelled on any port without that check.
- **Hooks already in a project's Claude Code settings** run outside the sandbox with your access. Opfence keeps the sandbox from writing `.claude/settings.json` and `.claude/settings.local.json`, and warns about hooks it finds there, but it cannot tell whether hooks a repository arrived with, or the scripts they run, are safe.
- **Open mode** tunnels every host that is not in the catalog without inspecting it. Strict mode, the default, refuses them.
- **git over SSH** to github.com is refused rather than inspected. Use HTTPS remotes under `opfence run`.
- **Behind a corporate proxy**, the proxy resolves host names, so Opfence can only refuse private IP addresses written literally; a name that resolves to an internal address is the corporate proxy's decision.

## Requests Opfence cannot read fully

These are never forwarded silently; they become `unknown` (which asks by default) or are blocked:

- Request bodies over 64 KiB, except a git push, whose ref updates are read from the first 64 KiB.
- WebSocket and other protocol upgrades to API hosts (blocked).
- Compressed request bodies other than gzip and deflate.
- Signed git pushes (`git push --signed`).
- AWS requests made with a placeholder key that Opfence cannot re-sign: presigned URLs, SigV4A (multi-Region) signatures, uploads with signed chunks, and bodies over 16 MiB without a hash header. These are blocked with a message saying why.
- AWS requests made with a placeholder key to hosts their creators run rather than AWS: API Gateway (`execute-api`), load balancers, EC2 public names and VPC endpoints. Opfence does not send your real key's signature there, so IAM-authenticated calls to your own API Gateway need a key Opfence does not hold.
- Request bodies that are neither JSON, a form nor multipart (plain text, binary uploads), and bodies over 64 KiB (a large Cloudflare Worker upload): rules that look at body fields treat them as `unknown`.

## What a decision cannot see

- **Force pushes.** A forced `git push` sends the same command as a normal one. Pushes to `main`, `master` and tag moves are treated as the worse case (`delete`); a force push to a feature branch counts as a `write`.
- **State the API hides.** When the class depends on something Opfence cannot see (whether an S3 bucket is versioned, whether a DynamoDB batch contains deletes), the catalog assumes the worse case. That can ask more than necessary; it does not ask less.
- **Operations missing from the catalog** get the provider's default (safe HTTP methods and GraphQL queries are usually reads) or `unknown`. A new endpoint that a provider ships as a `GET` with side effects would be classified as a read until the catalog learns it. A nightly check (`opfence catalog check-sources`) compares the catalog with the schemas providers publish and fails when one adds an operation that is not a read and that no rule covers, but only for providers that publish a schema and whose rules are marked complete (`coverage: full`); it cannot see endpoints a schema leaves out, and an MCP server's new tools are `unknown` until a rule names them.
- **SQL that hides its effect in the database.** `SELECT my_function()` is classed as a read unless the function is a known side-effect function or the same request creates it; a function, trigger or rule created earlier can do anything when it runs. A `WHERE` that reads a column counts as limiting even when it matches every row, apart from the cases Opfence recognises (`id = id`, `id IS NOT NULL` in its spellings, `id IN (id)`, `LIKE '%'` and match-all patterns, subqueries that never refer to the target's rows): `WHERE id > 0 OR id <= 0 OR id IS NULL` is a delete, not irreversible, and so is a subquery whose inner table shares the outer table's name (`DELETE FROM users WHERE EXISTS (SELECT 1 FROM users WHERE users.id = 1)`), which Opfence reads as correlated. SQL is read as Postgres, MySQL or SQLite, whichever the server speaks; SQL a parser cannot read keeps the rule's worst case. Turso's MCP tools keep a fixed class, because Turso does not publish their arguments. A query through PlanetScale's write tool is read as both MySQL and Postgres, since Opfence cannot tell which the database is: MySQL that is not also Postgres (backquoted names) keeps the tool's class and still needs confirming in production.
- **SQL summaries on cards are short.** A card names each statement's verb and up to three of the tables it acts on, and lists up to three statements. It names functions only when they are on Opfence's side-effect list, so `SELECT my_function()` reads as `SELECT` while the function may change anything (see above). The class, not the summary, is what the decision is made from.
- **A database's own protocol.** Postgres on 5432, MySQL on 3306 and Neon's WebSocket transport (the serverless driver's `Pool` and `Client`) are not read. Opfence reads the SQL that Neon's and PlanetScale's serverless drivers send over HTTPS; the databases' own connections are handled like any host outside the catalog: refused in strict mode unless you list the host under passthrough, tunnelled in open mode. Opfence reads which database these requests reach from the connection string's host (Neon) or the Basic-auth username (PlanetScale), never the password; map them in `opfence.yaml` or they count as production.
- **Redis.** Commands sent through Upstash's MCP server are classified one by one; Upstash's Redis REST API reached directly (the `@upstash/redis` SDK) is not, because its hosts (`<name>-<id>.upstash.io`) share a domain with QStash and Vector that no host pattern separates. Such requests are handled like any host outside the catalog. A Lua script (`EVAL`) is unknown, whatever it does; `KEYS *` is a read, however slow.
- **AWS CLI commands through the AWS API MCP server.** `call_aws` commands are read with awscli 1.46.0's command table and decided like the requests they make, but arguments given in a file (`--cli-input-json`, `file://`), as nested shorthand, or that awscli later adds are not read; such a command keeps the tool's irreversible class. Services outside `catalog/aws`'s twelve are decided by action name alone (reads by their `Describe`/`Get`/`List` names, everything else unknown), as through the proxy.
- **SQL that depends on the server's settings.** MySQL is read with backslash escapes on, as PlanetScale reads it; a server whose `sql_mode` turns them off reads `'a\'` differently. Opfence treats setting `sql_mode` or a character set as unknown, but cannot see one set earlier in the same session or on the server. MariaDB's `/*M! … */` comments are read as plain comments. A MySQL stored procedure, or a SQLite or MySQL function created earlier, can do anything when it runs; `CALL` is unknown, but a function called from a `SELECT` counts as a read unless it is one Opfence knows.
- **Secrets deep in a GraphQL query** are caught by field name (`graphql_secret_fields`, set for Fly.io). A secret field the list misses, or one on a provider without a list, is classified by the query's top-level field.
- **Form keys with `[]` in the middle** (`items[][price]=x`) are kept as one flat key, because servers disagree on how to group them, so a condition cannot see inside them. Indexed keys (`items[0][price]`) are read.
- **MongoDB filters.** An update with no filter or an empty one (`{}`) is irreversible; a filter that matches every document some other way (`{"_id": {"$exists": true}}`) is a write.
- **Phone approvals.** A push shows the operation, host, path and resource. It passes through the ntfy server (ntfy.sh unless you run your own) and through Google's or Apple's push service. Anyone who learns your push topic can answer requests, so treat it like a password: subscribe only on your phone, never in a browser or ntfy client on the computer the agent runs on (the agent could read the topic there), and `opfence phone setup --new-topics` replaces it. An ntfy access token given to `phone setup` travels in every push, because the buttons need one, unless the buttons get their own with `--button-token-stdin`: a token of a user that may only write the reply topic, so the push carries only that. A phone can deny a confirm but not approve it, and MCP tool calls the hook asks about are answered in Claude Code's own prompt, not on the phone. Each request costs two ntfy messages and ntfy.sh allows 250 a day per address without an account; an agent that keeps making requests that need approval can use that up (pushes are rate-limited to slow it down), after which requests are still held on your other channels. On iOS a push stays after the request ends, with buttons that no longer do anything.
- **Environments.** An operation is production unless your user config maps its ids to development or staging, so unmapped work asks more often, never less. A repository's `opfence.yaml` can only tighten.

## Credentials

- **Database passwords stay real.** The passwords in database URLs (`DATABASE_URL`, Neon's `Neon-Connection-String` header, PlanetScale's Basic auth) are not turned into placeholders, because the same passwords serve the databases' own protocol, which does not pass through Opfence; a placeholder would break those connections. Opfence still decides the SQL sent with them.
- **Keys Opfence does not hold stay real.** Keys the agent gets some other way (`~/.aws/credentials`, AWS SSO and roles, the `gh` CLI's keyring, cloud CLI config files, SSH keys) are not placeholders. Requests made with them still go through the same decisions; only key hiding is lost. `opfence init` reads `.env` files and MCP configs in the repository, not your home directory.
- **MongoDB Atlas API keys** (the Digest key pair) cannot be held, because the client signs each request with the private key; service accounts can. Under `opfence run` a service account's sign-in (`POST /api/oauth/token`) hands the agent a placeholder for the access token, which works for that session only; revoking it (`/api/oauth/revoke`, which takes the token in the body) sends the placeholder, which Atlas rejects. Outside the proxy (the hook, exports) the sign-in stays `credential`.
- **Secrets in responses** are removed only where a rule says where they are (`response.redact`), by JSON path. A field a provider adds or renames is passed through until the catalog learns it; the recorded responses in the catalog's tests check the paths against the documented shape, not against live traffic. A response held for transforming is buffered whole, up to 8 MiB.
- **Keys in Cursor's, VS Code's, Gemini CLI's and Codex's MCP configs** are reported by `opfence init` but left in place, because those tools also start their MCP servers without `opfence run`, where a placeholder would break them.
- **Scrubbing** replaces real key values in responses with their placeholders, including URL-encoded and base64-encoded copies, but not keys that an API splits in other ways (base64 broken into lines, or the first and last two bytes of a base64-encoded key). On AWS, a ranged read of an S3 object that holds a key can return pieces of it unscrubbed, because S3's downloads in parts need `Range`; other APIs have it removed.
- **The keychain.** On macOS any process running as you that can run `/usr/bin/security` can read Opfence's keychain items, and on Linux any process that can reach the session D-Bus can read Secret Service items. The sandbox is what keeps the agent away from them; `opfence doctor --probe` checks that it does.
- **Allowed operations can still move data.** Opfence classifies operations; it does not inspect what data a permitted write carries. An agent allowed to write to a development database or upload to a bucket can put anything it can read there.

## Approvals

- **MCP tool calls Claude Code makes** are asked in Claude Code's own prompt, which cannot make you type the resource name, so a `confirm` there is a plain ask. Calls those servers then make to catalog APIs go through the proxy and get the full `confirm`.
- **Codex** asks about MCP tool calls in its own prompt, so a `confirm` there is a plain ask too. When you approve a tool "for this session" in Codex, Codex stops prompting for that tool, so later calls Opfence would ask about go ahead (calls Opfence denies are still denied). With the approval policy `never`, Codex cannot ask, so Opfence denies what it would ask about.
- **Cursor's and Gemini CLI's local MCP servers.** Under `opfence run --srt` the requests these servers make to catalog APIs and databases go through the proxy and are decided there, but the tool calls themselves are not (no hook is installed): the approval card shows the API request rather than the tool and its arguments, and a tool whose effect stays on your machine is the sandbox's business, not Opfence's.
- **A human can approve the wrong thing.** The card shows the decoded operation, its class, environment and resource, but names such as a branch or a resource label are chosen by whoever made the request. Read the resource, not only the verb.
- **Approval fatigue.** Every `ask` interrupts you. Map your development ids so routine work is allowed there, and keep production asking.

## Outside Opfence's reach

- **Damage on your own machine**: deleted files, local databases, Docker containers. That is the sandbox's job (its filesystem rules), not Opfence's.
- **Code that runs later**: scripts, CI workflows, migrations or infrastructure files the agent writes and that run outside an Opfence session. Review them like any other change.
- **A compromised machine or Opfence binary.** Opfence runs as you; anything that already runs as you outside the sandbox, or as root, can change it, its trust store entries or its keychain items.
